## 1. 目的与范围

在已经用 vps-hardening 加固并确认的新 VPS 上，用 3X-UI v3.10.2 搭建一个 VLESS + REALITY 代理节点，供 5～8 人使用；通过带证书的订阅，把每个人的配置分发到基于 Mihomo 内核的客户端（Sparkle、FlClash、Clash Verge Rev）。

范围内：

- 按固定版本安装 3X-UI，面板只监听回环地址，只经 SSH 隧道访问；
- 一个 VLESS + REALITY 入站（443/tcp）；
- 每个使用者的客户端（UUID 和订阅 ID），以及停用和撤销；
- 订阅服务（2096/tcp，HTTPS），输出 Mihomo 配置；
- 订阅证书：经 Cloudflare 走 DNS-01 签发，并自动续期；
- 备份、恢复与迁移，3X-UI 的升级与回退；
- 只读检查和验收方法。

只适用于新机。已经在运行 3X-UI 的现网主机不在范围内，本仓库的任何步骤都不在现网主机上执行。范围外的事项见第 8 节。

**从 vps-hardening 继承的约定**（它的需求第 7.2 节，D14、D16、D32；本仓库的需求以这些为前提，不重复理由）：

- 安装 3X-UI 时带版本参数 `v3.10.2`，运行前按 vps-hardening 需求第 10.1 节的摘要校验 `install.sh`；
- 设 `XUI_ENABLE_FAIL2BAN=false`，不启用 IP Limit，Fail2ban 由 vps-hardening 管理；
- 用 `XUI_PANEL_PORT` 传入加固时记录的面板端口（默认 2053）。面板只监听 127.0.0.1（`x-ui setting -listenIP 127.0.0.1`），只经 SSH 隧道访问；
- 公开端口由管理员用 `vps-hardening ports --add` 开放，并从新的 SSH 会话确认。不使用 3X-UI 的防火墙菜单和 BBR 菜单；
- 80/tcp 不开放；Cloudflare API Token 保存在 VPS 上，只授予签发证书所需的最小权限；
- REALITY 回落等本机端口只监听 127.0.0.1；
- v3.10.2 自带的 Xray 只接受提供 X25519MLKEM768 的 REALITY 客户端，Mihomo 要设 `support-x25519mlkem768: true`。

## 3. 角色与场景

| 角色 | 说明 |
|---|---|
| 管理员 | 用户本人。以 root 用密钥登录 VPS，经 SSH 隧道使用面板，保管 Cloudflare API Token 和备份 |
| 使用者 | 5～8 人，在自己的设备上用 Mihomo 内核的客户端导入订阅 |
| Cloudflare | 托管域名的 DNS。签发证书时，acme.sh 经它的 API 写入验证用的 TXT 记录 |
| 证书颁发机构 | 默认为 Let's Encrypt（3X-UI 菜单的默认值），在方案设计中确定 |

| 场景 | 内容 |
|---|---|
| SC1 新建 | 在加固并调优后的 Debian 13 上安装 3X-UI，配置入站、使用者、证书和订阅，开放 443/tcp 和 2096/tcp，检查通过 |
| SC2 分发 | 管理员把每人自己的订阅地址发给本人；使用者在客户端导入，客户端定期更新 |
| SC3 使用者变动 | 新增、停用、删除使用者；某人的订阅地址泄露时，只重置这个人 |
| SC4 日常运行 | 证书自动续期；查看用量；定期或变更后执行检查 |
| SC5 迁移 | IP 被封或更换 VPS 时，在另一台新机上恢复配置，切换 DNS；使用者更新订阅后得到新的节点地址 |
| SC6 升级 | 3X-UI 发布新版本后，评估、备份、升级，失败时回退 |
| SC7 排查 | 连接失败时，按检查结果区分服务端、证书、订阅和客户端的问题 |

## 4. 功能需求

### FR-01 安装 3X-UI（P0）

- 按第 2.2 节继承的约定安装 v3.10.2。
- 面板的用户名、密码和 `webBasePath` 都是随机值，由管理员保存。
- 订阅证书配置完成之前不开放 2096/tcp：3X-UI 的订阅服务默认启用，对所有地址以 HTTP 提供（第 10.1 节）。vps-hardening 加固后 UFW 只放行 22/tcp，所以这一条只要求不要提前执行 `ports --add`。

验收：3X-UI 的版本为 v3.10.2；面板端口只在 127.0.0.1 上监听；没有 `3x-ipl` jail；`vps-hardening verify` 通过。

### FR-02 VLESS + REALITY 入站（P0）

- 只有一个入站：VLESS，443/tcp，安全层为 REALITY。传输方式和 flow 在方案设计中确定。
- REALITY 的密钥对和 shortId 在 VPS 上生成，私钥只保存在 3X-UI 的数据库中。
- 伪装目标（target 和 serverNames）选用第三方站点，选择标准和核实方法在方案设计中确定。
- 订阅中的节点地址必须直接到达 VPS：可以是 IP，也可以是在 Cloudflare 上不开启代理（DNS only）的主机名，不能是开启代理的主机名，因为 REALITY 不能经 Cloudflare 代理。3X-UI 在入站没有指定分享地址时，用请求订阅时的主机名作为节点地址（第 10.1 节），所以必须显式设置。

验收：
- 开启 ML-KEM 的 Mihomo 客户端，经订阅中的节点访问测试地址成功；
- 不开启 ML-KEM 时握手失败（按上游的行为，作为负面用例）；
- 节点地址解析到 VPS 的公网地址。

### FR-03 使用者（P0）

- 每个使用者对应一个 3X-UI 客户端，UUID 和订阅 ID 各自独立。本草案建议按人分配：同一个人的多台设备共用一个订阅。IP Limit 不启用，所以不限制设备数。
- 客户端名称（3X-UI 的 email 字段）使用代号，不用真实姓名或联系方式。
- 能停用、删除使用者；能单独重置某个人的 UUID 和订阅 ID。
- 流量上限和到期时间见 OQ-3。

验收：
- 停用之后，这个使用者的连接失败，订阅不再返回可用的节点；
- 重置之后，旧的订阅地址和 UUID 失效，其他人不受影响。

停用之后订阅具体返回什么，在方案设计中按 v3.10.2 的行为核实。

### FR-04 订阅（P0）

- 订阅服务在 2096/tcp 上只以 HTTPS 提供，证书覆盖订阅主机名。设置 `subDomain`，只应答这个主机名。
- 启用 Mihomo 格式（`subClashEnable`）。发给使用者的是 Mihomo 格式的地址（`/mihomo/<订阅 ID>` 或 `subClashPath`）。v3.10.2 生成的 Mihomo 配置会为 REALITY 写入 `support-x25519mlkem768: true`（第 10.1 节）。
- 原始链接格式在订阅启用时总是可用，链接中没有 ML-KEM 的设置。使用者不应导入原始链接，所以发给使用者的只有 Mihomo 地址（FR-11）。
- JSON 格式和内置订阅页面保持关闭（v3.10.2 的默认值）。
- 订阅路径用 3X-UI 初始化时生成的随机值。
- 保留 `Subscription-Userinfo` 等响应头，客户端据此显示用量和到期时间。
- 更新间隔默认 12 小时（`subUpdates`），是否调整在方案设计中确定。迁移之后，客户端最迟在一个间隔之后取得新的节点地址，使用者也可以手动更新。

验收：
- 从 VPS 之外取得订阅：证书链有效，主机名匹配；
- 返回的 YAML 能被 Mihomo 解析，只包含这个使用者的节点，REALITY 带 `support-x25519mlkem768: true`；
- 用 IP 或其他主机名访问时不返回订阅；不存在的订阅 ID 不返回节点。

### FR-05 证书（P0）

- 用 acme.sh 经 Cloudflare 走 DNS-01 签发，只覆盖订阅主机名。3X-UI 菜单还会同时签发通配符证书（第 10.1 节），这里不需要。
- 使用只限单个 Zone 的 API Token，不使用 Global API Key。具体权限组合在方案设计中按 acme.sh 的要求核实。Token 保存在 VPS 上，只有 root 可读。
- acme.sh 使用固定版本，不启用自动升级。3X-UI 菜单从 `get.acme.sh` 安装当时的最新代码，并开启 `--auto-upgrade`（第 10.1 节），与固定版本的做法不一致。
- 到期前自动续期，续期后订阅服务使用新证书。3X-UI 菜单默认在续期后执行 `x-ui restart`，所有连接会短暂中断（NFR-06）。
- 证书只用于订阅服务。面板只经 SSH 隧道访问，不配置证书。

验收：
- 证书有效，剩余天数超过 30 天；
- 续期演练（用测试 CA）成功，订阅服务随后使用新证书；
- acme.sh 的配置中没有 Global API Key。

### FR-06 端口（P0）

- FR-04 和 FR-05 完成之后，执行 `vps-hardening ports --add 443/tcp --add 2096/tcp`，并从新的 SSH 会话确认。
- 面板端口和 80/tcp 不开放。

验收：从 VPS 之外探测，22、443、2096 可达，面板端口和 80 被拦截；`vps-hardening verify` 通过。

### FR-07 只读检查（P0）

- 在 VPS 上以 root 执行，不改动任何文件、设置或服务。
- 检查项至少包括：
  - 3X-UI 的版本，面板的监听地址，Fail2ban 和 IP Limit 没有由 3X-UI 启用；
  - 入站的协议、端口、REALITY 设置和节点地址，本机端口的监听地址；
  - 订阅：只用 HTTPS，`subDomain` 已设置，Mihomo 格式已启用，JSON 格式和内置页面已关闭；
  - 证书的主机名和剩余天数；
  - acme.sh 的版本、自动升级、续期任务和 Token 的类型，Token 文件的权限；
  - `vps-hardening verify` 的结果。
- 输出中不出现秘密：UUID、订阅 ID、订阅路径、REALITY 私钥、面板凭据、`webBasePath` 和 Token。
- 3X-UI 的版本不是检查所针对的版本时，报告不符合，不再执行依赖它的数据格式的检查。
- 结果的分级和退出码与 vps-hardening 的 `verify` 保持一致，在方案设计中确定。
- 从 VPS 之外的验证：取得订阅并核对证书和内容，再用实际的客户端连接。用脚本还是手工步骤，在方案设计中确定。

验收：在符合本文的主机上全部通过；对每个检查项各注入一种偏差，检查都能发现（虚拟机测试）。

### FR-08 使用说明（P0）

- 覆盖 SC1～SC7：每一步的命令、面板中的取值、预期结果和核对方法。
- 在 shell 中输入 Token 等秘密的方式，不会把秘密留在命令历史中（例如 `read -rs`）。
- 只用文档保留的示例值（`example.com`、`192.0.2.x` 等），不出现真实的 IP、域名、订阅地址、UUID 和服务商名称。

验收：在测试 VPS 上按使用说明从新机完成 SC1，检查全部通过。

### FR-09 备份、恢复与迁移（P1）

- 备份 3X-UI 的数据库。数据库包含全部秘密，备份保存在 VPS 之外，由管理员加密保管。
- 在另一台按 vps-hardening 加固的新机上恢复：安装相同版本的 3X-UI，恢复数据库，签发证书，切换 DNS，开放端口，执行检查。
- 订阅主机名不变时，使用者不需要重新导入。

验收：在两台虚拟机之间完成一次迁移，使用者的订阅地址不变，更新订阅后连接成功。

### FR-10 升级与回退（P1）

- 3X-UI 的新版本先评估再升级：对照 vps-hardening 需求第 7.2 节的行为表和本文的检查项。v3.11.0 已于 2026-10-25 发布（第 10.1 节）。
- 升级前备份数据库；回退方式为重新安装原来的版本并恢复备份。

验收：在虚拟机中完成一次升级和一次回退，之后检查都通过。

### FR-11 客户端说明（P1）

- 为 Sparkle、FlClash、Clash Verge Rev 写明导入订阅的步骤和最低版本：内核须支持 REALITY 的 `support-x25519mlkem768`，即 Mihomo v1.19.10 及以后（第 10.1 节）。
- 写明只导入 Mihomo 格式的订阅地址。

验收：三个客户端各在一个平台上导入订阅并连接成功，平台在验证计划中确定。

## 5. 非功能需求

| 编号 | 优先级 | 需求 | 验收 |
|---|---|---|---|
| NFR-01 | P0 | 安全：面板不对外开放。订阅地址视同凭据：持有者能取得节点的全部参数，所以每人一个、可以单独撤销。秘密不进入日志、检查输出和仓库 | 测试中用测试秘密扫描输出和归档，命中即失败 |
| NFR-02 | P0 | 隐私：仓库中没有真实的 IP、域名、订阅地址、UUID、服务商名称和本地路径 | 每次推送前扫描 |

| NFR-04 | P0 | 与另外两个仓库兼容：完成 SC1 之后，`vps-hardening verify` 和 vps-tuning 的严格验证仍然通过 | 虚拟机测试 |
| NFR-05 | P0 | 固定版本：3X-UI 和 acme.sh 都使用固定版本，并校验摘要；升级按 FR-10 | 检查 |
| NFR-06 | P1 | 中断：证书续期和重启 x-ui 造成的连接中断在秒级 | 测试中记录时长 |
| NFR-07 | P0 | 检查只读、可以重复执行，结果只取决于主机的状态 | 测试中执行前后的状态摘要一致 |

## 6. 输入数据

| 输入 | 来源 | 说明 |
|---|---|---|
| 订阅主机名 | 管理员 | Cloudflare 上的完整域名 |
| 节点地址 | 管理员 | IP，或 DNS only 的主机名（FR-02） |
| Cloudflare API Token 和 Zone ID | 管理员 | 只限这个 Zone（FR-05） |
| REALITY 伪装目标 | 管理员 | 按方案设计的标准选择 |
| 使用者代号 | 管理员 | 5～8 个（D2） |
| 面板端口 | vps-hardening 的记录 | 默认 2053 |

在 VPS 上生成：面板凭据、`webBasePath`、REALITY 密钥对、shortId、UUID、订阅 ID 和订阅路径。

## 7. 与其他仓库的约定

- **vps-hardening：** 按第 2.2 节继承的约定。本仓库不改动 sshd、UFW 规则、Fail2ban 和自动更新的配置；公开端口只经 `vps-hardening ports` 开放。
- **vps-tuning：** 不使用 3X-UI 的 BBR 菜单；调优在安装 3X-UI 之前完成。
- **执行顺序：** 见 [README](../README.md)。

## 8. 范围外（P3）

- 其他协议和传输：VMess、Trojan、Shadowsocks、Hysteria2 等 UDP 协议、XHTTP、经 CDN 中转（D3）；
- 多个节点、3X-UI 的节点管理和订阅负载均衡；
- 面板对外开放，面板证书；
- IP Limit 和 3X-UI 自带的 Fail2ban；
- 3X-UI 的防火墙菜单和 BBR 菜单；
- 在已运行 3X-UI 的现网主机上执行任何步骤；
- 客户端本身的安装和更新。

### 10.2 风险

| 编号 | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R-1 | 订阅地址泄露 | 持有者能取得节点的全部参数，可以长期使用 | 每人一个订阅 ID，可以单独重置；只用 HTTPS；设置 `subDomain`；检查输出中不出现订阅地址 |
| R-2 | VPS 被攻破，Cloudflare API Token 泄露 | 攻击者能修改这个 Zone 的 DNS 记录 | Token 只限一个 Zone、只给签发所需的权限；可以在 Cloudflare 上随时撤销 |
| R-3 | acme.sh 自动升级 | 以 root 运行未经固定的上游代码 | 固定版本，不开启自动升级（FR-05） |
| R-4 | 客户端内核太旧 | REALITY 握手失败 | 写明最低版本（FR-11）；排查时先核对客户端版本 |
| R-5 | 使用者导入了原始链接 | 链接中没有 ML-KEM 的设置，连接失败 | 只发 Mihomo 地址（FR-04、FR-11） |
| R-6 | 节点地址指向开启了 Cloudflare 代理的主机名 | 连接失败 | 显式设置节点地址，检查核对它的解析结果（FR-02、FR-07） |
| R-7 | 3X-UI 升级后行为或数据格式变化 | 检查失效，或者升级后的默认值与本文不符 | 固定版本；先评估再升级；版本不符时检查报告不符合（FR-07、FR-10） |
| R-8 | 订阅服务在证书配置之前以 HTTP 监听所有地址 | 端口一旦开放，订阅内容会以明文传输 | 证书配置完成之前不开放 2096/tcp（FR-01、FR-06） |
| R-9 | IP 被封 | 节点不可用 | 迁移（FR-09）；订阅主机名不变时，使用者只需更新订阅 |

### 11.1 OQ-1 评估：交付形态

两种形态都要有检查。区别在于 3X-UI 中的设置由谁写入：

| 方面 | 脚本加验证（脚本写入设置） | 文档加只读检查脚本 |
|---|---|---|
| 写入方式 | 经 3X-UI 的 REST API（token 具有完全管理权限）或直接写数据库，写入入站、使用者和订阅设置 | 管理员按使用说明在面板中设置，shell 中的步骤照文档执行；脚本只读 |
| 配置的来源 | 脚本的声明和面板中的修改并存，要决定以谁为准：覆盖面板的修改，或者合并 | 只有 3X-UI 的数据库 |
| 日常操作 | 增减使用者要么经过脚本，要么造成偏差 | 照常在面板中操作，之后执行检查 |
| 3X-UI 升级 | 写入路径随接口和行为变化，每次升级都要重新验证写入和回滚 | 读取可能失效；失效时报告不符合，不会改坏配置 |
| 秘密 | 脚本要生成、传递或保存面板凭据、API token、REALITY 私钥、UUID 和订阅 ID | 秘密只在面板和数据库中，检查输出要遮蔽 |
| 新建和迁移的耗时 | 几分钟 | 新建约 30～60 分钟；迁移以恢复数据库为主，约 15～30 分钟（都是推断） |
| 人为失误 | 少 | 会有，由检查发现 |
| 开发和测试成本 | 高：幂等、输入校验、失败恢复和回滚都要实现和测试 | 中：检查项和注入偏差的测试。CI 中仍要用 API 布置测试用的 3X-UI，但只在测试中使用 |

**建议：文档加只读检查脚本。** 置信度：中高。3X-UI 的行为已对照源码核实；耗时和成本是推断，没有实测。理由：

1. 3X-UI 本身就是管理工具，它的数据库是配置的唯一来源。脚本再声明一份配置，就会和面板中的修改形成两个来源。
2. 变更不频繁：一台主机，5～8 个使用者，人员很少变动。自动化省下的时间主要在迁移上，而备份和恢复数据库（FR-09）已经能省下其中的大部分。
3. 失败时的后果不对称：只读检查最坏是报告错误；写入脚本出错则会改坏正在使用的配置。
4. vps-hardening 需要完整的应用、确认和自动恢复，是因为改错 SSH 和 UFW 会把管理员锁在外面。这里的操作不影响 SSH，不需要同样的机制。

**最强的反对理由：** 如果 IP 经常被封，迁移就会频繁发生；而且测试本来就要用 API 布置 3X-UI，写入脚本的一部分代码已经有了。

**重新评估的条件：** 出现以下任一情况时，先把 shell 中的步骤（安装、证书、恢复）改为脚本，面板中的设置仍保持手工：
- 新建或迁移超过每月一次；
- 检查多次发现同一种手工失误；
- 节点超过两台。

## 12. 验证方法

沿用 vps-hardening 的做法，具体内容在验证计划中确定：

- **CI 虚拟机：** Debian 13 amd64。测试代码用 API 布置 3X-UI，并在虚拟机中运行 Mihomo 实际连接。证书用测试 CA，不使用真实的 Token 和域名。
- **测试 VPS：** 真实的签发、订阅和客户端连接要用你的域名和 Cloudflare API Token，执行之前另行征求你的授权。
- **判定：** 按归档的证据逐项判定，不以 CI 显示通过为准。
