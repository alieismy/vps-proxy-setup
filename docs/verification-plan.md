## 1. 目的与范围

范围内：

- 在 CI 虚拟机（Debian 13 amd64，NFR-03）上验证 FR-01～FR-12、NFR-01～NFR-07 中能在虚拟机里验证的验收条件，以及方案设计中要用运行证据证实的推断（方案设计第 6 节）；
- 发布资产的完整性（方案设计第 4.8 节）；
- 规定测试 VPS 验收的内容。测试 VPS 上的操作要用户另行授权，本计划不授权执行。

范围外：

- Debian 12、Ubuntu 24.04 和 arm64（需求 NFR-03 中为 P2 或不在范围内）；
- 从中国大陆是否可达、是否会被识别或封锁。CI 测不到真实的封锁环境；测试 VPS 上客户端连接成功也只说明当时可用，不说明伪装有效（方案设计第 7.6 节）；
- 性能测量（NFR-06 只记录中断时长）；
- 第三方 target 自身的行为。CI 用替身（第 3.6 节），真实 target 只在测试 VPS 上观察。

## 2. 证据层次

| 层次 | 能证明 | 不能证明 |
|---|---|---|
| 源码核实 | 上游在固定版本中的实现逻辑 | 运行行为 |
| 静态检查 | 脚本语法、常见缺陷；仓库中没有秘密和真实标识 | 运行行为 |
| 虚拟机生命周期 | 在官方云镜像上、经加固和调优之后的端到端行为；经虚拟网络的可达性；外连边界上的连接 | 真实的 Tunnel、Cloudflare 边缘、真实 target、服务商网络 |
| 测试 VPS | 真实的 Tunnel、订阅发布、外部扫描、真实 target 和客户端 | 其他服务商和长期的封锁情况 |

报告时只陈述实际达到的最高层次，较低层次的证据不能代替较高层次。

## 3. 测试环境

### 3.1 平台

- Debian 13 amd64 的官方云镜像，按固定的 URL 和摘要下载（与 vps-tuning、vps-hardening 同源）。沿用 vps-hardening 的做法：在 `ubuntu-24.04` 运行器上，有 `/dev/kvm` 时用 KVM，否则用 TCG。
- 测试时会从官方仓库安装软件包，每次运行记录实际安装的版本。
- 每个作业的时长目标是 45 分钟以内（与 vps-hardening 相同），超出就拆分作业。

### 3.2 客体初始状态

主配置是一台加固并调优之后的新机，与 SC1 的前提相同（需求 A-1）：

1. cloud-init 写入测试密钥，root 用密钥登录；
2. 按 vps-tuning 的固定版本应用调优并重启验证，`90-proxy-vps.conf` 已预置（版本见 VO-6）；
3. 按 vps-hardening `v0.1.1` 加固并确认，UFW 只放行 22/tcp。

存量主机配置用于预检的拒绝用例，在主配置之上分别再加一项：

| 编号 | 附加条件 |
|---|---|
| S1 | 按第 3.5 节的固定版本直接运行 `install.sh` 装好了 3X-UI |
| S2 | 只有 3X-UI 的数据库文件，没有程序和服务单元 |
| S3 | 已安装 cloudflared |

每个会破坏状态的用例都运行在独立的 qcow2 覆盖层镜像上，互不影响。

### 3.3 网络与测试来源

| 来源 | 实现 | 用途 |
|---|---|---|
| 测试驱动 | 运行器经 QEMU 用户网络的端口转发连到客体：22、443、2053、2096、80，以及转发入站、3X-UI 的 api 入站、cloudflared metrics 和 Xray metrics 的端口 | 外部可达性、证书扫描 |
| 客户端命名空间 | 客体内的网络命名空间，经 veth 连接，用 `192.0.2.0/24`（RFC 5737） | 运行 Mihomo 和 FR-02 的探测；部署输入中的节点地址就是客体在这条 veth 上的地址 |
| 替身命名空间 | 客体内的另一个网络命名空间，经 veth 连接，用 `198.51.100.0/24`（RFC 5737） | target 替身和经代理访问的测试地址（第 3.6 节） |

- 客户端命名空间到 443 的连接走正常的入站路径，受 UFW 约束，要在 `vps-hardening ports --add 443/tcp` 之后才通。测试驱动代管理员执行这一步，并按 vps-hardening 的方式从新的会话确认。
- 部署的输入校验要接受文档地址作为节点地址（可以警告，不能拒绝），否则 CI 无法测试。这一点交给详细设计。
- 测试只使用文档保留地址和 `example` 域名，不出现真实地址和域名。

### 3.4 测试秘密

- 每次运行生成一个随机的 Tunnel 测试令牌（格式与真实令牌相同，连不上 Cloudflare）。它同时是泄露扫描的标记字符串。
- 3X-UI 生成的面板凭据、`webBasePath`、REALITY 私钥、UUID、订阅 ID 和订阅路径，由测试驱动在客体中从交给管理员的文件和只读打开的数据库读出，只用作扫描清单，不写入归档。测试驱动要改面板设置时（第 3.6 节的例外、VT-36～VT-38、VT-71），用交给管理员的文件中的凭据登录面板接口。
- 数据库文件、交给管理员的文件和令牌文件不归档，只归档它们的摘要、属主和权限（第 6 节）。

### 3.6 target 替身与测试地址

FR-02 的用例要有一个 target。CI 不连第三方站点，用替身：

- **地址。** 替身在替身命名空间的 `198.51.100.0/24` 上，客体的 `/etc/hosts` 把 `target.example`、`other.example` 和 `probe.example` 解析到它。
- **测试专用的例外。** 3X-UI 模板中 `direct` 出站的 `finalRules` 屏蔽 `geoip:private`，它来自发布包自带的 `geoip.dat`，其中的 `private` 包含 RFC 5737 的三个地址段和 `2001:db8::/32`（第 11 节）。所以任何文档地址上的替身都会被屏蔽；生产中的 target 是公网地址，不受这条屏蔽影响。测试驱动在 `deploy` 和 VT-16、VT-70 之后，在 `finalRules` 的最前面加一条只放行替身这一个地址的规则；`finalRules` 按顺序取第一条匹配的规则（第 11 节），其余地址仍被屏蔽，占位地址 `127.0.0.1` 的保护不受影响。这是对被测配置的偏离：每次运行在归档中记录；`check` 不检查 `finalRules`（方案设计第 7.6 节），结果不受影响；测试 VPS 上不加这条例外。不可行时的替代方案见 VO-2。
- **TLS。** 替身支持 TLS 1.3 和 h2，证书由每次运行生成的测试 CA 签发，覆盖 `target.example` 和 `other.example` 两个虚拟主机。两个虚拟主机返回可区分的内容。虚拟主机之间的路由可以切换为"严格按 SNI"或"按 Host 交叉路由"（VT-81）。
- **观测。** 替身记录收到的每个 TCP 连接和 TLS SNI，作为 FR-02 外连边界上的证据之一（第 4.4 节）。
- **测试地址。** `probe.example`（HTTP 和 HTTPS）是经代理访问的测试地址，不依赖外网。
- **客户端的分流规则。** 连接类用例让 Mihomo 用全局模式，使结果不受客户端分流规则的影响：客户端规则把私有地址和私有域名直连，测试名和测试地址可能落在其中（推断）。分流规则本身由 VT-42 单独验证。

### 3.7 外网依赖

以下用例需要运行器和客体能访问外网，下载失败记为环境失败（第 6 节）：下载镜像和固定版本的程序；Mihomo 下载规则集（VT-42）；回国流量规则的测试域名和 IP 从发布包自带的 Geo 数据中选取（VT-30），VT-42 的国外测试地址要经代理实际访问。

### 4.4 REALITY 与转发限制（FR-02，方案设计第 4.4、7.4 节）

FR-02 的负面用例在外连边界上观测，三处证据都要有：转发入站的访问日志（路由到 `blocked`）、替身的连接记录（没有这条连接）、客体在替身命名空间 veth 上的抓包（没有到替身的 SYN）。只看客户端拿不到内容不算通过（需求 FR-02）。Xray 的访问日志由测试驱动在部署之后打开，与第 3.6 节的例外一样记为测试环境的偏离。本节的探测都从客户端命名空间发往节点地址的 443。

| 编号 | 需求 | 场景 | 通过判据 | 里程碑 |
|---|---|---|---|---|
| VT-20 | FR-02 | 开启 ML-KEM 的 Mihomo 导入订阅，经节点访问 `probe.example` | 访问成功；Mihomo 配置中 `client-fingerprint` 为 `chrome`，`flow` 为 `xtls-rprx-vision`，带 `support-x25519mlkem768: true` | M2 |
| VT-21 | FR-02 | 同一配置去掉 `support-x25519mlkem768` | 握手失败（上游行为，负面用例） | M2 |
| VT-22 | FR-02 | 读取订阅中的节点 | 节点地址是部署输入的 IPv4 地址，不是主机名；节点名称等于入站备注，按 UTF-8 字节比对国旗完整 | M2 |
| VT-23 | FR-02 | 用 `other.example` 作 SNI 连接 | 客户端拿不到 `other.example` 的内容；外连边界的三处证据都表明没有转发 | M2 |
| VT-24 | FR-02 | 不带 SNI 的 ClientHello（`openssl s_client -noservername`） | 同 VT-23 | M2 |
| VT-25 | FR-02 | 不是 TLS 的输入：明文 HTTP 带 `Host: target.example`；随机字节 | 同 VT-23。前者证明 `destOverride` 只有 `tls` | M2 |
| VT-26 | FR-02 | 用 `target.example` 作 SNI、普通的 ClientHello | 被转发到替身：客户端拿到替身的证书和 `target.example` 的内容，替身有这条连接 | M2 |
| VT-27 | FR-02，SR-3 | SNI 为 `target.example` 的未认证连接，ClientHello 分别：拆成多个 TLS 记录；在一个记录内分三段以上发送，段间隔逐步加大到 300ms；带 X25519MLKEM768 的大 ClientHello。每种 20 次 | 每种 20 次全部被转发到替身。不通过时按方案设计第 4.4 节决定，M2 的判定见第 7 节 | M2 |
| VT-28 | FR-02 | 异权威探测：用 `target.example` 的 SNI 建立 TLS，再请求 `Host: other.example` 和 HTTP/2 `:authority: other.example` | 记录结果。替身严格按 SNI 路由时拿不到 `other.example` 的内容（结果干净不作为隔离的证明，需求 FR-02） | M2 |
| VT-29 | FR-02 | 从客体直接访问替身，与经节点的 443 访问替身（SNI 为 `target.example`）对照：握手、证书、ALPN、响应 | 记录差异和取舍，不作为通过判据 | M2 |

## 5. 测试 VPS 验收（M3、M5）

测试 VPS 上的操作要用户另行授权；在 Cloudflare 上增删路由也要在授权范围内。以下只是验收内容，不是操作手册。

- **前提：** 一台重装为 Debian 13 的测试 VPS，按需求 A-1 加固并调优；一个从未以 DNS only 方式指向节点 IP 的测试订阅主机名；Tunnel 的令牌；target 按需求第 11.5 节在这台 VPS 上选择，并用 `target-check` 核实。服务商名称、真实地址、主机名和 target 只记在私有记录中，不进仓库。
- **M3（Tunnel）：**
  - 部署的第 8 步等到 `/ready` 就绪；`check` 全部 PASS；
  - 从 VPS 之外经订阅主机名取得订阅：证书链有效，主机名匹配；三个客户端拉取订阅时不被 Cloudflare 的挑战挡住（方案设计 SR-5）；
  - Tunnel 路由的偏差注入（FR-07）：在控制台临时加一个公开主机名，指向本机一个没有服务监听的回环端口（不指向面板，以免面板暴露到公网），`check` 报告 FAIL；删除之后恢复 PASS，并确认对应的 DNS 记录也已删除；
  - 经 Tunnel 访问不到面板和其他本机服务；从 `/config` 核实兜底规则（方案设计第 7.5 节的推断）；
  - 停止 cloudflared 时订阅不可取，REALITY 正常；启动后订阅恢复，记录时长（NFR-06）；
  - cloudflared 以动态用户运行（OD-3）；不可行时按 SR-8 处理并记录。
- **M5（验收）：**
  - 按使用说明从新机完成 SC1（FR-08）；`check` 全部 PASS，退出码 0；
  - 从 VPS 之外扫描公网地址（有 IPv6 时两种地址都扫）：只有 22、443 可达，没有任何端口出示含订阅主机名的证书（FR-06）；
  - 对真实 target 重做 VT-23～VT-29，其中 serverNames 之外的 SNI 用与 target 同一网络的另一个站点：在 VPS 上转发入站的外连侧观测，为此临时打开的访问日志在测试结束后关闭，日志文件删除；
  - 三个客户端在 VO-5 确定的平台上导入订阅并连接成功，记录客户端显示的内核版本（FR-11）；
  - 回国流量规则：客户端用全局模式访问国内目标失败，国外目标成功；
  - 停用和重置使用者各一次（FR-03）。
- **不能证明：** 从中国大陆的长期可达性，以及不被识别或封锁。
